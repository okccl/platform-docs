# ADR-010: IDP設計（Keycloak / Backstage 選定）

## Context

PlatformチームとアプリケーションチームのRole要件を一人二役で再現するという構成上、認証・認可の仕組みを実際に動かして検証したいという動機があった。単にNamespaceやRBACを設定するだけでなく、SSOとアクセス制御を含めた権限モデル全体を試すことを目的とした。

一方、開発者体験の改善については現職での課題意識が出発点にある。環境払い出しのスクリプト化は進んでいたが、開発チームからの依頼はExcelの申請書経由であり、これを改善したいという問題意識があった。その文脈でBackstageのScaffolder（Golden Path）が有効な解決策として浮上した。

2つの目的から、OIDCアイデンティティプロバイダーの選定と開発者IDPの選定という独立した意思決定が発生した。

## Options

### OIDCアイデンティティプロバイダー

**Option 1: Keycloak**
- **Pros:** グループ・ロール・カスタムクレームなど高度な権限制御が可能なOSS IdP。ArgoCD・Backstage等との統合実績が豊富。
- **Cons:** 設定項目が多く、導入・運用のコストが高い。

**Option 2: Dex**
- **Pros:** シンプルなOIDCフェデレーションレイヤー。軽量でKubernetes環境への統合が容易。
- **Cons:** 権限制御の機能が限定的で、グループ・ロール管理の学習目的には範囲が狭い。

**Option 3: 外部SaaS（Auth0 / Okta 等）**
- **Pros:** 運用不要でSSOをすぐに実現できる。
- **Cons:** オンプレ環境には適さない。現職（Tanzu）・ポートフォリオともにオンプレ前提のため選択肢に入らなかった。

### 開発者IDP

**Option 1: Backstage**
- **Pros:** CNCF Incubatingプロジェクト。Scaffolderによるセルフサービス型Golden Pathの実現、Software Catalog、TechDocs等の機能を持つOSS。
- **Cons:** 導入しただけでは使える状態にならず、テンプレート・プラグイン・認証統合など自前での作り込みが多い。プラグインのメンテナンスコストも継続的に発生する。

**Option 2: 商用IDP（Port / Cortex 等）**
- **Pros:** セットアップが容易でUIが整っている。
- **Cons:** SaaSベースの製品が中心で、オンプレ環境の現職（Tanzu）への展開に適さない。ポートフォリオでSaaSを採用すると現職への転用可能性が下がる。

## Decision

**OIDCアイデンティティプロバイダーにKeycloakを採用する。開発者IDPにBackstageを採用する。**

## Reasons

### Dexを選ばなかった理由

シンプルさが特長だが、権限制御の機能が限定的で学習対象として範囲が狭かった。現職でKeycloakの導入検討が進んでいたこともあり、どうせ学ぶなら現場で使うことになるKeycloakを先行して学習しようと判断した。

### Keycloakを採用した理由

直接のきっかけは現職での採用検討だった。自分の担当ではなく知識がない状態だったため、近い将来に使う可能性が高い中で学習目的でポートフォリオに導入した。また、PlatformチームとDevチームの一人二役という構成上、グループ・ロールベースの本格的な権限制御を実際に動かして理解する必要があり、多機能なKeycloakが目的に合致していた。

### 商用IDPを選ばなかった理由

Port・Cortex等の主要製品はSaaSベースであり、オンプレ環境で稼働する現職（Tanzu）への転用ができない。そもそも比較検討の土台に乗らなかった。

### Backstageを採用した理由

現職での課題意識が出発点だった。環境払い出しはスクリプト化されていたが、開発チームからの依頼はExcelの申請書で行われており、この体験を改善したいという問題意識があった。Backstage ScaffolderでGolden PathをセルフサービスUIとして実現できると知り、現職での検証・提案準備と並行してポートフォリオ環境にも導入した。

現職ではアプリ数が10を超えておりSoftware Catalogの需要も出始めているが、現段階では開発チームの余力を考慮してScaffolderによる環境払い出しにスコープを絞っている。Catalog等のさらなる活用は今後の提案対象として位置付けている。

## Consequences

**ポジティブ:**
- Scaffolderによるfullstack Golden Path（FastAPI + React）のE2E動作を確認し、Excel申請書に替わるセルフサービスフローを実装できた。現職への展開・提案に向けた具体的な検証知見が得られた。
- KeycloakによりArgoCD・BackstageのSSOを統合し、グループ（platform-team / app-developer）ベースのRBAC制御を実際に動かすことができた。現職での導入検討に対して自分の言葉で話せる知識が身についた。
- 将来的にBackstageを組織横断的に使う場合、Keycloakの権限制御との相性が良いことを実装を通じて把握できた。

**ネガティブ・トレードオフ:**
- Backstageは導入しただけでは使える状態にならず、自前での作り込みが多い。機能を追加するたびにメンテナンスコストも発生するため、想定以上に運用負荷が高かった。
- 現職への展開では開発チームの余力を考慮して利用スコープをScaffolderに絞った。採用・展開のスコープは組織の余力と優先事項を確認してから決めるべきという教訓が得られた。
