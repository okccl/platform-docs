# ADR-011: ポリシーエンジン選定（Kyverno）

## Context

現職ではKyvernoを部分的に導入していたが、本格的には活用できていなかった。また、アプリによってリソース制限の記述が抜けているケースがあり、仕組みとして統制できていないという課題を感じていた。latestタグの使用がトラブルの原因になった経験もあり、こうしたガードレールをポリシーとして強制する仕組みをポートフォリオ環境で検証することにした。

## Options

**Option 1: Kyverno**
- **Pros:** KubernetesネイティブなポリシーエンジンでCRDとしてポリシーを定義する。Kubernetes標準のYAML構文に近く、既存のマニフェスト管理の延長で書ける。Validate（違反時に拒否）とMutate（自動変換）の両方をサポートする。
- **Cons:** ポリシー適用範囲が広いため、テスト・デバッグ用途のリソースにも適用されてしまい、例外設定の管理コストが発生する。

**Option 2: OPA Gatekeeper**
- **Pros:** OPAエコシステムの一部として、Regoによる汎用的なポリシー記述が可能。
- **Cons:** Regoの学習コストが高く、Kubernetes特有の文脈で使うにはKyvernoより習得が難しい。

## Decision

**ポリシーエンジンにKyvernoを採用する。**

## Reasons

**Kyvernoを採用した理由**

Kubernetes標準のYAML構文に近い書き方でポリシーを定義できるため、既存のマニフェスト管理の延長として学習・運用できる。OPA GatekeeperはRegoという独自言語の習得が必要で、Kubernetesのリソース定義と文脈が分離してしまう。Kyvernoは宣言的なYAMLで書けるため馴染みやすく、まずKyvernoで検証しようと判断した。

**ValidateとMutateの使い分け**

本ポートフォリオ環境では以下の方針で使い分けている。

- **Validate:** `latest`タグの使用禁止・resourcesフィールド（limits/requests）の記述必須を強制。意図的に省略しているマニフェストを検知・拒否するために使用。
- **Mutate:** 新規Namespace作成時に自動でラベルを付与し、監視対象などのスコープ制御に使用。現職ではノードへの自動ラベル付与で同様の用途が使われており、Kubernetesの運用パターンとして実用的な使い方と判断した。

## Consequences

**ポジティブ:**
- リソース制限の記述漏れとlatestタグの使用を、GitOpsのPR段階ではなくAdmission段階で機械的に弾けるようになった。ポリシーをCRDとして管理することでGitOps管理下に置けるため、ガードレールの変更履歴も追跡できる。
- 現職での部分的な導入に留まっていたKyvernoを、Validate・Mutateの両面で一通り使う経験を積めた。

**ネガティブ・トレードオフ:**
- テストやデバッグ用のPodもポリシー違反として弾かれてしまい、作業効率が落ちる場面があった。本番環境で導入する際は、検証Namespaceへの例外設定やExclude設定が必要で、「ポリシー導入後に使う人の作業が増えた」と感じさせないための設計と運用整備が重要だと認識した。
