# ADR-008: Observabilityスタック選定（LGTMスタック）

## Context

Kubernetesクラスタの可観測性を確立するにあたり、メトリクス・ログ・トレースの3本柱を揃える必要があった。現職ではLoki / Grafana / Prometheusに加えDatadog・Sysdigを併用しており、ツールの実運用経験がある状態で選定に臨んだ。

ポートフォリオのローカル開発環境という制約（リソース制限・個人費用）を前提に、「現場でそのまま通用する技術選択」を基準とした。

## Options

### Option 1: 商用SaaS（Datadog / Sysdig 等）

- **Pros:** GUIがリッチで視認性が高い。Sysdigはランタイム脆弱性チェックなど、Observability以外の機能も含む統合プラットフォームとして機能する。
- **Cons:** 個人のdev環境に商用ライセンスを投じる合理性がない。機能面ではLGTMスタックで代替できないことはほぼない（脆弱性チェックはTrivyで対応）。

### Option 2: ELK系スタック（Elasticsearch + Kibana 等）

- **Pros:** ログの全文検索・分析に特化しており、アプリが全文検索を多用するユースケースでは実績がある（現場でも開発者向けにその用途で導入済み）。
- **Cons:** Elasticsearchのリソース消費（大きなヒープ要件）と運用の複雑さが難点。Platform側としてObservabilityに活用した経験がなく、利用する動機が見えない。

### Option 3: LGTMスタック（Prometheus / Grafana / Loki / Tempo）

- **Pros:** 現職でPrometheus / Grafana / Lokiの実運用経験がある。OSS中心で個人環境のコスト制約に合う。クラウド移行後も同スタックを継続利用できる。
- **Cons:** 作り込み時のGUIの洗練度は商用に劣る。

## Decision

**LGTMスタック（Prometheus / Grafana / Loki / Tempo）を採用する。**
コレクターはGrafana Alloyを採用する。

なお、長期メトリクス保存のためのMimirは設計段階で検討したが、リソース消費を問題視して採用しなかった。

## Reasons

### 商用SaaSを選ばなかった理由

現職でDatadogおよびSysdigの実運用経験があり、GUIの視認性の高さは認める。ただし個人のdev環境に商用ライセンスを投じる合理性がなく、Observabilityの本質的な機能はLGTMスタックで代替できると判断した。脆弱性チェックという点ではSysdigの役割をTrivyで補っている。

### ELK系を選ばなかった理由

現場では開発者向けにアプリの全文検索高速化を目的として導入した経験があるが、Platform側としてObservabilityに活用した経験はない。利点が見えていない一方、Elasticsearchのリソース消費と運用の複雑さは把握しており、リソースが限られるローカル環境では選択肢に入れなかった。

### LGTMスタックを採用した理由

1. **現場での実運用経験がある**
   Prometheus / Grafana / Lokiはすでに現場で使っており、スタックとしての動作を把握している。未検証だったTempoとMimirの検証も兼ねて採用した。

2. **Mimirはリソース消費を理由に除外した**
   分散メトリクスストレージとして設計されたMimirは、単一ノードのローカル環境に対してオーバーエンジニアリングと判断した。現状のPrometheusによる短期保存で十分。

3. **Tempoはトレース検証目的で導入した**
   現場にはTempoがなかったため、検証を兼ねて導入した。ただし分散トレーシングはアプリ側のインストルメンテーション改修が前提になるため、現場への導入提案は開発チームがトレーシングを必要とするかどうかに依存すると判断している。

### Grafana Alloyをコレクターに選んだ理由

現場ではPromtailを使っており、ログ収集にはなじみがあった。ただしPromtailはGrafana公式がAlloyへの移行を推奨しており、実際に現場でPromtail→Alloy移行を担当した経験がある。両者の動作を把握した上で、公式推奨に従いAlloyを採用した。

## Consequences

**ポジティブ:**
- 現場での実運用経験があるため、スタック全体のトラブルシュートに迷いがない
- kube-prometheus-stackのデフォルトダッシュボードが即時利用可能で、導入直後からそれなりに使える状態になる
- DBバックアップ失敗のアラートをDiscordに通知するなど、実際の運用用途で機能している

**ネガティブ・トレードオフ:**
- 商用SaaSに比べてGUIの洗練度は低く、ダッシュボードを作り込もうとすると手間がかかる
- 実際のログ確認は`kubectl logs`で直接行うことが多く、Lokiを積極的に活用する機会は限られている
- Tempoによる分散トレーシングはアプリ側のインストルメンテーションが必要なため、現場への展開は開発チームの意欲次第になる
